# Railway cloud spellbook

Enabled at the owner's request, 2026-09-11. Local IndexedDB saves remain the immediate write path; cloud upload runs after archive changes (2-second debounce), every 15 seconds while open, and on reconnect. No folder picker. Existing archives backfill automatically after unlocking the room. The app must be open and online to finish uploads.

Storage: Railway service incant-web, persistent volume ec7b4c53-48a3-414f-804c-e74164febb70 mounted at /data. The server uses RAILWAY_VOLUME_MOUNT_PATH/incant-backup-v1; an explicit INCANT_BACKUP_PATH is available for local integration tests. Missing configuration returns 503, never an ephemeral fallback.

Images are SHA-256-addressed data URLs. Each immutable JSON snapshot links its exact source image, every generated image, spells, timestamps, device identifier, sketch bundle and session. An upload acknowledges only after file fsync, atomic rename and directory fsync. Snapshots are committed after referenced objects. Retries are idempotent. Earlier snapshots have no delete endpoint. The server index is consulted on each sync rather than trusting a browser-only uploaded flag.

The spellbook displays upload status and exposes Back up now and Recover cloud spellbook. Recovery verifies image hashes, combines generations of an identical source, imports into separate archive rows and does not change the live drawing or active-page metadata. Repeated recovery reuses recovered rows. Recovered copies do not recursively upload themselves. The recovery interface currently includes historical source snapshots and may show a recovered copy alongside an existing local original.

Access uses the existing authenticated room cookie and same-origin API protections. This is one shared room archive: anyone who can unlock the room can recover its cloud spellbook. It is not a multi-user account isolation system. Credentials and content are not included in evidence logs. Local and cloud copies are independent; a Railway volume survives deployments, but this is not yet a second-provider disaster-recovery system or a scheduled Railway volume-snapshot policy.

Verification: qa-cloud-backup passes build, 9 unit/contract tests and 38 browser tests. Synthetic tests cover interrupted uploads, hash mismatch, incomplete manifests, restart persistence, no duplicate upload, exact-byte recovery, and preserving the active draft. Production verification is recorded separately; synthetic evidence alone does not prove the owner's device uploaded.
